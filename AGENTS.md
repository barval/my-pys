# AGENTS.md

Требования к проекту `my-pys` («Моя персональная Яндекс Станция») и правила
работы ИИ-агентов в этом репозитории.

## 1. О проекте

Проект превращает Яндекс Станцию Лайт 1-го поколения в голосовую колонку:
Яндекс отвечает за сервисы (погода, музыка, умный дом, звонки, радионяня),
остальные запросы уходят во внешнюю LLM через локальный OpenAI-совместимый
роутер и Quasar Bridge.

Основные компоненты:

- `llm-router` — локальный LLM-роутер на `5002`;
- `webui` — Flask-панель в Docker на `127.0.0.1:8080`;
- `router-control`, `stand-control` — узкие sidecar'ы для Docker;
- `tts` — локальный Piper TTS для кнопки «Сказать»;
- `lite-kit` — стенд прошивки и root (запускается только на время настройки);
- колонки — Yandex Station Lite с Quasar Bridge.

## 2. Версия

- Формат версии — **`vX.Y`**, без третьего компонента.
- Текущая версия — **`v2.1`**.
- Источники версии:
  - `VERSION` — `v2.1`;
  - `webui/__init__.py` — `__version__ = "2.1"`;
  - `README.md` — строка «Версия»;
  - `CHANGELOG.md` — раздел версии;
  - git-тег — `2.1` (без префикса `v`).
- Версия в интерфейсе и `/healthz` — `2.1`.
- При смене версии обновлять все перечисленные места одновременно.

## 4. Приватные данные — запрещено коммитить

В git **не должны** попадать:

- реальные имена колонок и комнат;
- реальные IP-адреса, подсети и MAC-адреса;
- Device ID и серийные номера;
- токены, API-ключи, пароли, хеши паролей;
- SSH-ключи и `known_hosts`;
- архивы резервных копий;
- содержимое `secrets/`, `local/`, `backups/`, `router-state/`,
  `webui-state/`;
- логи и дампы с приватными значениями.

В документации, тестах и примерах использовать только синтетические данные:

- имена: `speaker-a`, `speaker-b`, `speaker-c`, `speaker-d`;
- комнаты: `Комната A`, `Комната B`;
- IP/подсети: `192.168.1.x`, `10.0.0.x`;
- MAC: `02:00:00:00:00:01` (локально администрируемый диапазон);
- Device ID: `EXAMPLE000000000000000000000001`;
- токены: `sk-router-test`, `EXAMPLE-TOKEN`.

Перед коммитом проверять:

```bash
git status --short
git ls-files secrets local backups router-state webui-state
git grep -nIE 'sk-[A-Za-z0-9]{20,}|BEGIN OPENSSH|PRIVATE KEY'
```

При сомнении — спросить владельца проекта, можно ли публиковать файл/данные.

## 5. Код

- Комментарии — **только по делу и на русском языке**. Не пересказывать код,
  не оставлять декоративные баннеры и английские пояснения.
- Docstring'и — на русском, если они нужны; очевидные удалять.
- Не оставлять мёртвый код: неиспользуемые функции, поля, импорты, шаблоны,
  JS-обработчики, endpoint'ы без потребителей.
- Не менять `vendor/` без явной необходимости.
- Соблюдать существующий стиль и структуру.
- Изменения — минимальные и по задаче; не рефакторить соседний код.
- Ошибки для пользователя — на русском.
- Не логировать секреты; `redact` должен маскировать значения из `secrets/`.

## 6. Тесты и проверки

Хост может убивать процессы при нехватке RAM. Запрещены тяжёлые прогоны без
явного разрешения пользователя.

Перед pytest:

```bash
pgrep -c pytest        # должно быть 0
free -h                # желательно >= 4 ГБ свободно
```

По умолчанию запускать только узкие проверки:

```bash
python3 -m pytest webui/tests/test_app.py -q -k "конкретный_тест"
python3 -m pytest webui/tests/test_<модуль>.py -q
python3 -m pytest router/tests/test_router.py -q
```

Не запускать два pytest одновременно и не запускать в фоне.

Статические проверки:

```bash
ruff check webui router scripts
python3 -m compileall -q webui router scripts
bash -n scripts/*.sh
```

## 7. Команды

```bash
make router            # собрать и запустить llm-router
make router-stop       # остановить роутер

make webui             # собрать и запустить панель, TTS и sidecar'ы

```

Тесты панели — `make webui-test` (полный прогон; запускать только с
разрешения). Тесты роутера — `make router-test`.

## 8. Веб-панель и CLI

Два равноправных способа настройки:

- **веб-панель** — основной;
- **командная строка** — альтернативный.

Оба должны выполнять одинаковую последовательность:

1. подготовка хоста: прошивка, стенд, DNS роутера;
2. сброс и привязка колонки;
3. добавление колонки/профиля;
4. ADB и root;
5. SSH и отключение OTA;
6. маршрут и ключ;
7. Quasar Bridge;
8. маршрутизация Bridge;
9. проверка LLM и голосом;
10. остановка стенда и возврат DNS.

При первом запуске без профилей панель открывает `/start` («Быстрый старт»):
шаги 1–3, затем мастер колонки с шага 4.

Меню панели: «Колонки», «Модели и доступ», «Проверка», «Настройки»,
«Дополнительно».

При изменении одного из способов проверять, что второй и документация
описывают тот же порядок и те же скрипты.

## 10. Подготовка к релизу

По запросу «подготовить всё к релизу» выполнить:

1. `git status --short` — рабочее дерево должно быть понятным.
2. Проверить отсутствие приватных данных (раздел 4).
3. Сверить версию во всех источниках (раздел 2).
4. Проверить актуальность README, docs, навыка и CHANGELOG.
5. Проверить отсутствие мёртвого кода и английских/шумных комментариев.
6. Проверить соответствие web/CLI сценариев.
7. Узкие тесты затронутых модулей + `ruff` + `compileall` + `bash -n`.
8. Обновить `CHANGELOG.md` (перенести `[Unreleased]` в выпуск, если нужно).
9. Сделать коммит(ы) с понятными сообщениями.
10. При необходимости — тег `X.Y` и пуш.

## 11. Новый релиз

По запросу «подготовить релиз X.Y»:

1. Создать ветку `vX.Y` от текущей рабочей ветки (если её нет).
2. Обновить версию:
   - `VERSION` → `vX.Y`;
   - `webui/__init__.py` → `__version__ = "X.Y"`;
   - README — строка версии;
   - CHANGELOG — новый раздел `[X.Y]` с датой;
   - при необходимости — упоминания версии в docs/skills.
3. Проверить, что старые ссылки на версию не остались.
4. Выполнить проверки из раздела 10.
5. Закоммитить, создать тег `X.Y`, запушить ветку и тег.
