# Моя Яндекс Станция

**My Personal Yandex Station** — неофициальный проект, не связан с Яндексом.

**Версия:** v2.0.0 (ветка `v2.0`)

Проект превращает Яндекс Станцию Лайт 1-го поколения в голосовую колонку,
где **Яндекс** отвечает только за погоду, время, музыку и умный дом, а все
остальные запросы уходят во **внешнюю LLM** с OpenAI-совместимым API ([FLAI](https://github.com/barval/flai),
Ollama, vLLM, LM Studio или облачный сервис). Используется **Quasar Bridge**
в режиме `hybrid`: голос и распознавание речи по-прежнему облачные.

> Это не полная приватность: аудио всё равно уходит в облако Яндекса для
> распознавания и синтеза речи.

## Важно: риск и ответственность

для **ваших собственных** колонок. Не применяйте их к чужим устройствам,

риск**. Возможны потеря данных и настроек, полная или частичная

проблемы с аккаунтом и другие последствия.

## Перед началом

Понадобится:

- своя Яндекс Станция Лайт 1-го поколения;
- хост с Docker и этим репозиторием — в примерах он `192.168.1.2`;
- доступ к роутеру, чтобы менять DNS для колонки;
- телефон с приложением «Дом с Алисой»;
- прошивка `.46` — её скачает `./scripts/fetch-firmware.sh`;
- понимание рисков из раздела выше.

Перед первым запуском сохраните `local/`, `secrets/` и `backups/` —
это настройки хоста. Сброс колонки их не удаляет, но свои данные на
колонке (`/data`) он очистит.

## Веб-панель: быстрый старт

Если колонки уже настроены, ручные команды нужны только для первичной
прошивки и сброса. Дальше удобнее через панель.

```bash
make router        # LLM-роутер, если ещё не запущен
make webui         # панель и sidecar'ы
make webui-passwd  # задать пароль
```

Откройте `http://127.0.0.1:8080` и войдите с этим паролем.

- Сменить пароль: экран «Пароль» или `make webui-passwd`.
- Доступ с других устройств: `WEBUI_BIND=0.0.0.0 make webui`.
- Остановить панель: `make webui-stop`.
- Логи: `make webui-logs`.
- Проверка: `curl -s http://127.0.0.1:8080/healthz`.

Разделы панели:

- **Колонки** — статус, Bridge, routing, ключ, SSH/OTA.
- **Прошивка** — скачать образ, запустить/остановить стенд, найти
  колонку и выполнить действия после root.
- **LLM-роутер** — основной и запасные маршруты отдельными строками.
- **Ключи** — промежуточные токены и upstream-ключи.
- **Бэкапы** — шифрованные архивы всей конфигурации или одной колонки.
- **Аудит** и **Пароль**.

Сброс кнопкой и привязка в «Дом с Алисой» остаются ручными.

## Полный порядок настройки

Точные команды и пояснения — в `docs/03-runbook.md`. Ниже — общий
порядок, чтобы было понятно, что происходит и в какой момент.

### 0. Проверить LLM-роутер

```bash
make router-init
make router
make router-status
make check
```

Роутер должен отвечать на `http://192.168.1.2:5002/v1`. Если upstream
ещё не выбран, настройте маршрут в `secrets/router-routes.json` или через
веб-панель.

### 1. Скачать прошивку и поднять стенд

```bash
./scripts/fetch-firmware.sh
./scripts/start-lite-kit.sh
dig +short @192.168.1.2 quasar.yandex.net
```

Прошивку также можно скачать из веб-панели: вкладка «Прошивка» →
«Скачать прошивку».

Последняя команда должна вернуть `192.168.1.2`. Стенд `lite-kit` — это
отдельный контейнер, который отдаёт колонке нужную прошивку и включает
ADB с root. Он работает на хосте и требует Docker.

### 2. Подготовить сеть

- Выключите из розетки остальные колонки, чтобы стенд не задел их.
- Закрепите MAC → IP в DHCP роутера.
- На роутере поставьте DNS `192.168.1.2` для этой сети.
- Перезагружать роутер не нужно: DNS применится к следующему
  DHCP-запросу колонки.

### 3. Сбросить колонку

Сброс обязателен для DNS-метода. Он очищает `/data`, отвязывает колонку
от аккаунта и удаляет установленный софт.

1. Отключите питание колонки, подождите несколько секунд.
2. Включите питание и **сразу** зажмите кнопку паузы (▶‖).
3. Держите 6–10 секунд, пока подсветка не станет жёлто-зелёной.
4. Отпустите: колонка перейдёт в режим настройки.

### 4. Привязать колонку

Перед каждой следующей колонкой полностью закройте и снова откройте
«Дом с Алисой» — иначе Bluetooth-сопряжение не проходит.

1. Включите Bluetooth и геолокацию на телефоне.
2. **Выключите Wi-Fi на телефоне**, оставьте мобильный интернет и
   Bluetooth.
3. «Дом с Алисой» → «+» → «Устройство с Алисой».
4. Дойдите до экрана выбора Wi-Fi, введите сеть и пароль.
5. Подключайтесь: колонка обратится к стенду `192.168.1.2`.

Если DNS указан неверно или стенд недоступен, привязка сорвётся. В этом
случае проверьте DNS, логи стенда и повторите сброс.

### 5. Перепрошивка и ADB

После привязки колонка сама скачает с стенда нужную прошивку, установит
её и включит ADB с root. Это и есть «перепрошивка» в этом проекте:
отдельно вручную образ не заливается. Скачивание и установка занимают
несколько минут — не выдёргивайте питание.

Проверка:

```bash
adb connect "$(./scripts/resolve-speaker.sh):5555"
adb shell id
```

Должно быть `uid=0(root)`. Если ADB нет — см.
`docs/05-troubleshooting.md`: DNS, логи стенда, версия прошивки.

### 6. SSH и отключение OTA

```bash
./scripts/post-root-ssh.sh
```

Скрипт установит Dropbear и SSH-ключ, отключит OTA и перезагрузит
колонку. После перезагрузки проверьте вход по ключу и статус OTA.

### 7. Bridge, routing и ключ

```bash
./scripts/install-quasar-bridge.sh --non-interactive
./scripts/apply-bridge-routing.sh
./scripts/set-speaker-key.sh
make status
make check-backends
```

Эти же действия для выбранной колонки есть на вкладке «Прошивка» в
веб-панели.

Bridge подключается к локальному LLM-роутеру, а не напрямую к
провайдеру.

### 8. Проверить голосом

- «Алиса, какая завтра погода?» — отвечает Яндекс.
- «Алиса, почему небо голубое?» — отвечает внешняя LLM.

## Несколько колонок

Профили колонок — это отдельные файлы окружения. Публичный пример лежит в
`config/speakers/example.env`; реальные профили храните в
`local/speakers/<имя>.env` — папка `local/` исключена из git.

| Пример профиля | IP | Device ID |
|---|---|---|
| `local/speakers/speaker-a.env` | `192.168.1.101` | `EXAMPLE...001` |
| `local/speakers/speaker-b.env` | `192.168.1.100` | `EXAMPLE...002` |
| `local/speakers/speaker-c.env` | `192.168.1.102` | `EXAMPLE...003` |
| `local/speakers/speaker-d.env` | `192.168.1.103` | `EXAMPLE...004` |

Имена и количество профилей произвольны: скрипты читают любой файл,
переданный через `SPEAKER_ENV`.

Для любой команды по конкретной колонке:

```bash
SPEAKER_ENV=local/speakers/speaker-b.env ./scripts/post-root-ssh.sh
SPEAKER_ENV=local/speakers/speaker-b.env ./scripts/install-quasar-bridge.sh --non-interactive
SPEAKER_ENV=local/speakers/speaker-b.env ./scripts/apply-bridge-routing.sh
SPEAKER_ENV=local/speakers/speaker-b.env make status
```

Без `SPEAKER_ENV` используются переменные из `local/.env` (или `.env` в
корне, если локального файла нет).

IP в профиле — только подсказка для ускорения поиска. Привязка идёт по
`SPEAKER_DEVICE_ID`/`SPEAKER_MAC`; `resolve-speaker.sh` проверяет MAC и не
использует IP как идентификатор колонки.

## LLM-роутер

Все колонки ходят на один адрес:

```text
http://192.168.1.2:5002/v1
```

Роутер по промежуточному ключу выбирает upstream. Подходит любой
OpenAI-совместимый сервис: локальный (Ollama, vLLM, LM Studio), облачный
API или собственный сервер. Колонку при смене провайдера трогать не
нужно.

```bash
make router-init   # создать ключи колонок и secrets/router-routes.json
make router        # собрать и запустить контейнер llm-router
make router-status # health
make router-logs   # логи
```

Ключи лежат **только на хосте** в `secrets/` (gitignored, chmod 600):

| Колонка | Промежуточный ключ | Файл upstream-ключа |
|---|---|---|
| `speaker-a` | `secrets/router-token-speaker-a` | `secrets/upstream-token-speaker-a` |
| `speaker-b` | `secrets/router-token-speaker-b` | `secrets/upstream-token-speaker-b` |
| `speaker-c` | `secrets/router-token-speaker-c` | `secrets/upstream-token-speaker-c` |
| `speaker-d` | `secrets/router-token-speaker-d` | `secrets/upstream-token-speaker-d` |

Имя upstream-файла задаётся в `api_key_file` маршрута. Это может быть
любое имя: `upstream-token-speaker-a`, `openai-token-speaker-a`,
`local-llm-token` и т.п. Если в существующем конфиге указано другое имя,
используйте его.

`secrets/router-routes.json` — таблица маршрутов. Пример без секретов:
`config/router-routes.example.json`. Если upstream-ключ ещё не создан,
маршрут отвечает `503`, остальные колонки работают.

Профиль колонки указывает только на промежуточный ключ:

```env
LLM_BASE_URL=http://192.168.1.2:5002/v1
LLM_TOKEN_FILE=secrets/router-token-speaker-b
```

Записать адрес и ключ в колонку:

```bash
SPEAKER_ENV=local/speakers/speaker-b.env ./scripts/set-speaker-key.sh
```

Скрипт обновляет `QUASAR_LLM_BASE_URL`, `QUASAR_LLM_MODEL` и
`QUASAR_LLM_API_KEY` в `/data/opt/quasar-bridge/runtime.env`, затем
перезапускает Bridge.

### Fallback

У каждого маршрута может быть до **9** резервных upstream в массиве
`fallbacks` (в порядке попыток). Порядок меняется стрелками ↑/↓ в
веб-панели:

```json
"fallbacks": [
  {
    "base_url": "https://api.example.com/v1",
    "api_key_file": "fallback-token-speaker-a",
    "model": "your-fallback-model",
    "history": "client"
  }
]
```

Старый одиночный `"fallback"` тоже читается для совместимости.
Если основной маршрут недоступен, отдаёт `429`/`5xx` или не ответил за
таймаут, запрос уходит в первый доступный fallback, затем в следующий.
Тело пересобирается под режим каждого upstream: для `history=server`
уходит только текущий вопрос, для `history=client` — окно Bridge.
Изменения `secrets/router-routes.json` применяются без перезапуска.

### Проверка доступности

В панели на вкладке «LLM-роутер» есть кнопка «Проверить доступность». Она
дергает у каждого upstream `GET {base_url}/models` с его ключом и
таймаутом 3 секунды:

- зелёный «живой» — HTTP 2xx;
- красный «ошибка» — HTTP 401/403/5xx и т.п.;
- красный «недоступен» — таймаут или сетевая ошибка;
- серый «нет ключа» — файл ключа отсутствует или пуст;
- «не проверено» — проверка ещё не запускалась.

Это диагностика, а не постоянный мониторинг. Если провайдер не
поддерживает `/models`, статус будет ошибочным, хотя обычный чат может
работать. Роутер всё равно проверяет доступность при реальном запросе и
переключается на fallback по `fallback_on`.

### История и сессии

- `history=server`: роутер отправляет **только последний вопрос** и
  стабильный `user`, историю хранит провайдер. Подходит для сервисов с
  серверной историей.
- Некоторые провайдеры (например, [FLAI](https://github.com/barval/flai)) склеивают роли в один текст и
  могут пересказывать служебные инструкции. Поэтому для них
  system-промпт не отправляется. Это особенность провайдера, а не
  роутера.
- Health-check `make check-backends` пишет в отдельную сессию
  `voice-health`, поэтому «Ответь одним словом: связь» не появляется в
  основном диалоге.
- `history=client`: уходит окно Bridge — 6 ходов, 12k символов, TTL 5 минут.
- Сессия upstream одна на колонку. После 30 минут простоя начинается
  новая; автоматически остаются текущая и две предыдущие сессии.

### Краткость ответов

Для голоса роутер обрезает ответы любой LLM до **3 предложений / 400
символов** и убирает Markdown. Настройка — в начале
`secrets/router-routes.json`:

```json
"response": {
  "max_sentences": 3,
  "max_chars": 400,
  "strip_markdown": true
}
```

Обрезаются только не-stream ответы (`stream: false`); Bridge использует
именно такой режим.

Новый Bridge `0.6.2-chunked` присылает заголовок
`X-Quasar-Voice-Chunking: 1`. Для таких запросов роутер отдаёт до
**3000 символов**, а Bridge сам режет ответ на куски по ~500 символов
(до 6 кусков) и озвучивает их подряд. Старые Bridge без заголовка
продолжают получать 3/400.

Собрать кастомный Bridge:

```bash
./scripts/build-quasar-bridge.sh
```

Установщик автоматически берёт `v0.6.2-chunked`, если сборка есть в
`.cache/release-v0.6.2-chunked/`; явно задать версию можно через
`QUASAR_VERSION`.

Лимиты чанкинга на колонке:

```env
QUASAR_SPEECH_MAX_CHARS=500
QUASAR_SPEECH_MAX_CHUNKS=6
```

### Streaming-озвучка

Streaming включается на колонке:

```env
QUASAR_STREAM_LLM=1
```

Bridge открывает streaming-сессию сразу, держит колонку пустыми
deferred-сообщениями каждые 3 секунды и начинает TTS с первого готового
предложения. Idle-таймаут SSE — 90 секунд, чтобы пережить долгий ответ
upstream.

Если первого текста нет долго, Bridge говорит короткую фразу-заполнитель:
первая через **10 секунд**, затем каждые **15 секунд**. Список и тайминги
настраиваются:

```env
QUASAR_SPEECH_FILLER=1
QUASAR_SPEECH_FILLER_AFTER=10
QUASAR_SPEECH_FILLER_EVERY=15
QUASAR_SPEECH_FILLER_MAX=3
QUASAR_SPEECH_FILLERS="Секунду, ищу ответ.|Пока думаю.|Мне нужно чуть больше времени.|Ещё немного, и смогу сказать."
```

Заполнители замолкают, как только приходит первый реальный текст.

### Upstream-ключи

Ключ провайдера хранится в файле, указанном в `api_key_file` маршрута.
Для каждой колонки удобно использовать отдельный ключ и отдельного
пользователя у провайдера, если он это поддерживает.

Формат:

```bash
printf '%s\n' 'sk-...' > secrets/upstream-token-speaker-b
chmod 600 secrets/upstream-token-speaker-b
```

После этого маршрут `speaker-b` станет доступен автоматически. Проверка:

```bash
SPEAKER_ENV=local/speakers/speaker-b.env ./scripts/check-llm.sh
SPEAKER_ENV=local/speakers/speaker-b.env make status
```

`make status` проверяет только процесс Bridge. `make check-backends`
дополнительно дергает LLM тестовым запросом «Ответь одним словом: связь».

## Веб-панель: подробности

Панель — Flask-приложение в Docker. На хосте не нужны Python, Flask, ssh
или adb: всё внутри контейнеров. Панель не получает полный Docker API.

### Запуск и проверка

```bash
make router        # LLM-роутер
make webui         # панель, router-control и stand-control
make webui-passwd  # пароль администратора
```

`make webui` пересоздаёт контейнеры и собирает образы. `llm-router` и
`lite-kit` в этот стек не входят: роутер запускается `make router`, а
стенд — кнопкой на вкладке «Прошивка».

Проверка:

```bash
docker compose -f docker/docker-compose.webui.yml ps
curl -s http://127.0.0.1:8080/healthz
make webui-logs
```

`/healthz` возвращает версию — по ней видно, что запущен актуальный код.

Если запускаете compose вручную, задайте путь к репозиторию:

```bash
HOST_REPO_PATH=$(pwd) docker compose -f docker/docker-compose.webui.yml up -d --build
```

`make webui` подставляет `HOST_REPO_PATH` автоматически.

### Вход и пароль

Пароль хранится как scrypt-хеш в `secrets/webui-admin.hash` (`0600`).
Задать или сменить его:

```bash
make webui-passwd
```

Или в панели: раздел «Пароль». После смены текущая сессия завершается.
Если пароль утерян, `make webui-passwd` задаёт новый.

### Доступ по сети

По умолчанию порт слушается только на `127.0.0.1`. Для доступа с других
устройств локальной сети:

```bash
WEBUI_BIND=0.0.0.0 make webui
```

Не публикуйте порт в интернет. Если нужен HTTPS, ставьте панель за
локальный nginx.

### Разделы

- **Колонки** — профили с полными MAC/device ID, моделью и цветной
  иконкой; статус, проверка LLM, ключ, routing, Bridge, SSH/OTA.
- **Прошивка** — скачивание образа, список файлов, запуск/остановка
  `lite-kit`, поиск колонки и действия после root.
- **LLM-роутер** — создание маршрута, отдельные строки для основного и
  запасных upstream, добавление/редактирование/удаление fallback.
- **Ключи** — ротация промежуточных токенов и запись upstream-ключей.
- **Бэкапы** — шифрованные архивы всей конфигурации или одной колонки.
  Архив включает ключи и SSH-ключ, поэтому защищён паролем.
- **Аудит** — последние действия администратора.
- **Пароль** — смена пароля.

### Адреса в командах

Команды на вкладке «Прошивка» и адрес роутера подставляются из
`local/.env`: `ROOT_STAND_IP` и `LLM_BASE_URL`. Если их нет, используется
публичный пример `192.168.1.2`. Поэтому в панели должен отображаться
реальный адрес вашего стенда, а не значение из README.

### Безопасность

- Репозиторий монтируется в панель только для чтения; `secrets/`,
  `webui-state/`, `backups/`, `.cache/` и каталог прошивок — read-write.
- `router-control` умеет только перезапускать `llm-router`.
- `stand-control` умеет только запускать, останавливать и показывать
  статус `lite-kit`.
- Оба sidecar доступны только по внутренней сети и не публикуют порты.
- `stand-control` использует Docker socket, потому что запускает
  `lite-kit` с `network_mode: host`. Это привилегированная операция:
  запускайте стенд только когда он действительно нужен, и останавливайте
  после прошивки.
- Панель и стенд должны работать только в локальной сети.

Подробности — в [`docs/07-webui.md`](docs/07-webui.md).

## Безопасность

- `secrets/` исключён из git. Не коммитьте ключи роутера и upstream-ключи.
- LLM-сервер не должен быть доступен из интернета. Ключи передаются по локальной сети, поэтому изолируйте порт и используйте отдельные ключи.
- SSH на колонке по умолчанию с пустым паролем. После настройки добавьте
  свой публичный ключ и уберите `-B` из Dropbear.
- Сброс стирает `/data` и отвязывает колонку от аккаунта.
- Прошивка `.46` скачивается со стороннего зеркала; проверяйте CRC32/SHA-256.

## Откат

На колонке по SSH:

```sh
sh /data/opt/quasar-bridge/app/control.sh rollback
reboot
sh /data/opt/quasar-bridge/app/uninstall.sh
```

Вернуть обновления Яндекса: `sh /data/opt/yandex-noupdate.sh restore`.
Остановить стенд: `./scripts/stop-lite-kit.sh`, вернуть DNS роутера.

## Если что-то пошло не так

Сначала определите, жива ли колонка: горит ли подсветка, отвечает ли
Алиса, видна ли колонка в приложении. От этого зависит путь
восстановления.

### 1. Колонка жива, но Bridge, SSH или ADB работают неправильно

Не спешите со сбросом. Если SSH ещё доступен, попробуйте мягкий откат:

```sh
pkg=/data/opt/quasar-bridge/app
sh "$pkg/control.sh" status
sh "$pkg/control.sh" logs
sh "$pkg/control.sh" rollback
reboot
```

Если после перезагрузки Алиса снова отвечает как раньше, удалите Bridge:

```sh
sh "$pkg/uninstall.sh"
```

Верните обновления Яндекса, если отключали:

```sh
sh /data/opt/yandex-noupdate.sh restore
```

Остановите стенд и верните DNS роутера: `./scripts/stop-lite-kit.sh`.

Если SSH/ADB уже не отвечают — переходите к сбросу.

### 2. Сброс до заводских настроек

Сброс — основной «тяжёлый» способ вернуть колонку в рабочее состояние,
если она включается и реагирует на кнопку, но не пускает по SSH/ADB,
Алиса молчит или установленный Bridge мешает работе.

Что делает сброс:

- очищает `/data` — установленный Bridge, ключи, ADB-маркеры и локальные
  настройки;
- отвязывает колонку от аккаунта и переводит её в режим настройки;
- обычно возвращает штатное поведение Алисы.

Чего сброс не гарантирует:

- он не всегда удаляет правки rootfs в `/system` — например, init-скрипт
  SSH или отключение OTA. Если они мешают, нужен
  `yandex-noupdate.sh restore` или перепрошивка;
- он не поможет, если колонка не включается или не грузится («кирпич»).
  В этом случае нужен factory/recovery-образ и перепрошивка через стенд.

Перед сбросом сохраните всё важное:

- на хосте — `local/`, `secrets/` и архив из панели `/backup`;
- на колонке, если SSH ещё работает — нужные файлы из `/data`.

Порядок сброса:

1. Отключите питание колонки, подождите несколько секунд.
2. Включите питание и **сразу** зажмите кнопку паузы (▶‖).
3. Держите 6–10 секунд, пока подсветка не станет жёлто-зелёной.
4. Отпустите кнопку — колонка перейдёт в режим настройки.
5. Привяжите колонку заново в «Дом с Алисой»: Bluetooth и мобильный
   интернет на телефоне, Wi-Fi телефона выключить, приложение полностью
   перезапустить.
6. Если нужны модификации — повторите настройку по
   `docs/03-runbook.md`.

Если сброс не завершился:

- повторите сброс;
- DNS включайте только на экране выбора Wi-Fi;
- закройте приложение и выключите Wi-Fi на телефоне;
- если колонка не привязывается — см. `docs/05-troubleshooting.md`.

### 3. Колонка не включается или не грузится

Это худший сценарий. Не выдёргивайте питание во время прошивки.
Factory-recovery обычно остаётся целым, но восстановление требует
recovery-режима, перепрошивки factory-образом или `.46` через стенд.
Если нет опыта работы с recovery — лучше обратиться в сервис, а не
экспериментировать вслепую.

### 4. Что будет с настройками хоста

Сброс колонки не удаляет `local/`, `secrets/` и `backups/` на хосте.
После сброса:

- профиль колонки остаётся, но Bridge, SSH и ADB на самой колонке нужно
  установить заново;
- старые ключи можно использовать снова или ротировать;
- если device ID и MAC не изменились, `resolve-speaker.sh` найдёт колонку
  по ним, а не по IP.
